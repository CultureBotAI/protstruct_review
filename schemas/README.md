# `schemas/` — LinkML schema for protstruct_review

<!-- catalog-state: tasks=T01–T17; count=17; drivers=17 -->

This directory holds the LinkML schema that describes every machine-loadable record produced by the harness:

- the **catalog** of T01–T17 structural-biology tasks (`ref/catalog.yaml`),
- the **EvaluationRun** records that capture per-artifact measurements and headline findings (`data/examples/eval/EVAL_*.yaml`),
- the **QualityDataSheet** snapshot per structure (`data/examples/qds/QDS_*.yaml`).
- the standalone **structural-criteria and PassCriterionBinding registry**
  (`ref/structural_criteria.yaml`).

The denormalized TSVs (`ref/tasks_and_evaluations.tsv`, `EVAL_*_metrics.tsv`,
`EVAL_*_headline.tsv`) are optional human-facing exports from the YAML records, not the validated
form. Their absence does not invalidate a canonical YAML evaluation record.

## Files

| File | What it is |
|---|---|
| `protstruct_review.yaml` | The schema itself. Single file at v0; split into `core.yaml` / `catalog.yaml` / `eval.yaml` once it grows past ~600 lines or a second consumer needs only a subset. |
| `README.md` | This document. |
| `structural_criteria.yaml` | A **second, standalone** schema (own tree_root `CriteriaCollection`) for self-describing per-criterion entries and contextual `PassCriterionBinding` rows — whole-cell threshold-registry locator, operand/unit, applicability, preconditions, and effective/supersession lineage. Instances live in `ref/structural_criteria.yaml`; validated separately in `scripts/validate.sh`. |

## Quick-start: validate

```bash
# Validate everything in one go.
bash scripts/validate.sh

# Validate one record by hand.
linkml-validate --schema schemas/protstruct_review.yaml \
    data/examples/eval/EVAL_1sar_cdba2c07_2026-04-24.yaml
```

`linkml-validate` (LinkML 1.9.6) infers the target class from the YAML structure when the schema declares a `tree_root`. The `Container` class in this schema is the tree root and accepts any subset of `catalog_tasks`, `tools`, `metric_definitions`, `structures`, `experimental_data`, `agent_artifacts`, `evaluation_runs`, `quality_data_sheets`, `qds_replay_pins`, `tool_recommendations`, and `assumptions`.

## Quick-start: regenerate Pydantic models

```bash
gen-pydantic schemas/protstruct_review.yaml > protstruct_review/models.py
python -c "from protstruct_review.models import EvaluationRun, QualityDataSheet"
```

The committed `protstruct_review/models.py` is the pinned API surface for downstream Python tooling. Re-run `gen-pydantic` whenever the schema changes.

## What is NOT generated or committed

- **JSON Schema (`gen-json-schema`).** Output drifts on every LinkML version bump and adds churn to PR diffs. Regenerate locally on demand: `gen-json-schema schemas/protstruct_review.yaml > /tmp/protstruct.schema.json`.
- **OWL / SHACL / GraphQL.** Out of scope at v0. Add when an external consumer asks.

## Authoring conventions

- **Single source of truth = YAML.** TSVs are derived. The catalog `ref/catalog.yaml` is canonical; `ref/tasks_and_evaluations.{md,tsv}` is regenerated by `scripts/records_to_tsv.py`.
- **Measurement values are typed.** `agent_claim`, `oracle_measure`, and `delta` use the `TypedMeasurementValue` class with exactly one of `{value_numeric, value_text, is_not_applicable=true}` populated. Source carriers cannot contain QDS lineage/verdict fields. The TSV→records loader at `scripts/tsv_to_records.py` is the canonical cell parser; do not hand-edit measurements. Referential integrity also enforces each MeasurementValue's metric↔task, tool↔task, and tool↔family coherence from source snapshots first and the live catalog only as fallback.
- **References, not inlining.** Class-typed slots default to FK-style serialization (`structure_ref: 1sar`), not nested objects. Sub-summaries on `QualityDataSheet` (identity_block / geometry_summary / etc.) are explicitly `inlined: true` since they are not stand-alone entities.
- **Identifiers are loose strings.** `EvaluationRun.id` and `QualityDataSheet.id` accept any string. The filename convention from `ref/eval_naming.md` lives on `eval_filename_stem`, not on the canonical id, so future suffixes (`_v2`, `_oracle-update`) don't require a schema bump.

## Evolving the schema

1. Edit `schemas/protstruct_review.yaml`.
2. Run `bash scripts/validate.sh` — every existing record must still validate.
3. If a class was renamed or a slot was removed: update `scripts/tsv_to_records.py`, `scripts/records_to_tsv.py`, and `scripts/qds_emit.py` together.
4. Regenerate Pydantic models: `gen-pydantic schemas/protstruct_review.yaml > protstruct_review/models.py`.
5. Commit schema + models + scripts in one commit.

> **Status (2026-07-20): the threshold is well past — the schema is ~2,100 lines and still one
> file.** The split is deliberately deferred, not forgotten. The second trigger has not fired: there
> is still exactly one consumer (`gen-pydantic` → `protstruct_review/models.py`), and no downstream
> needs a subset. Splitting now would add five files and an import graph while every editor still
> loads the whole thing. Revisit when a second consumer appears — a JSON-Schema export for an
> external validator, or a catalog-only reader — since that is what makes the seam pay for itself.

When the schema crosses ~600 lines or a second consumer needs only a subset, split into:

```
schemas/
├── core.yaml           # mixins, identifier slots, common enums (Stage, ToolFamily, …)
├── catalog.yaml        # CatalogTask, Tool, MetricDefinition (imports core)
├── eval.yaml           # EvaluationRun, MeasurementValue, HeadlineFinding (imports core)
├── qds.yaml            # QualityDataSheet + sub-summaries (imports core, eval)
└── index.yaml          # tree_root: Container, imports the rest
```

Update validation invocations to use `schemas/index.yaml` once split.

## Round-trip sanity check

```bash
python scripts/records_to_tsv.py ref/catalog.yaml --kind catalog -o /tmp/catalog_export.tsv
diff <(cut -f1-9 ref/tasks_and_evaluations.tsv) /tmp/catalog_export.tsv
# empty diff means the YAML round-trips bit-for-bit to the existing TSV
```
